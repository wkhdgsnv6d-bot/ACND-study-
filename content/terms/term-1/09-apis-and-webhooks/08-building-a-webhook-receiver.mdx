terminology:
  - term: "Signature"
    definition: "A hash of the request body combined with a shared secret, sent in a header, which proves the sender knew the secret and that the body was not altered."
  - term: "Signing secret"
    definition: "A value known only to you and the vendor, used to produce and verify signatures. Distinct from an API key."
  - term: "Raw body"
    definition: "The exact bytes the vendor sent, before any parsing. Signature verification must use these, not a re-serialised object."
  - term: "Replay attack"
    definition: "Capturing a valid signed request and sending it again later to make the same thing happen twice."
  - term: "Timestamp tolerance"
    definition: "A window — typically five minutes — outside which a signed request is rejected as too old, limiting replay."
  - term: "Constant-time comparison"
    definition: "Comparing two secrets in a way that takes the same time regardless of where they first differ, so timing cannot reveal the secret."
  - term: "Acknowledge then process"
    definition: "Returning 200 immediately on receipt and doing the real work afterwards, so the vendor does not time out and retry."

reviewConcepts:
  - key: signature-verification
    prompt: "What does verifying a webhook signature prove, and what does it not prove?"
    answer: "It proves the sender knew the shared signing secret and that the body was not altered in transit — so the event genuinely came from the vendor and says what they sent. It does not prove the event is recent, which is why a timestamp check is needed to limit replay, and it does not prove the event is new: a legitimate signed event can be delivered twice by the vendor's own retry, so idempotency is still required."
  - key: raw-body-rule
    prompt: "Why must signature verification use the raw request body?"
    answer: "Because the signature is a hash of the exact bytes the vendor sent. Parsing JSON and re-serialising it changes whitespace, key order and number formatting, so the hash no longer matches even though the data is identical. Most frameworks parse the body before your handler runs, so you have to explicitly capture the raw bytes — and the symptom of getting this wrong is an invalid signature on a payload that looks perfectly correct."
  - key: ack-then-process
    prompt: "Why acknowledge a webhook before doing the work, and what does that require?"
    answer: "Because vendors time out in a few seconds and retry what they think failed. If the full workflow runs before you respond, one slow downstream call pushes you past the timeout and every event starts arriving twice. So respond 200 as soon as the signature verifies, then process asynchronously — via a queue, a stored row, or the platform's own async step. It requires that failures after acknowledgement are still visible, since the vendor now believes the event was delivered and will not retry it."
  - key: webhook-idempotency
    prompt: "How do you make webhook processing idempotent, and why is it not optional?"
    answer: "Record the vendor's event id on receipt and ignore any event whose id you have already processed — storing it with a unique constraint so the check is atomic rather than a read-then-write race. It is not optional because delivery is at-least-once by design: a response that arrives after the vendor's timeout causes a retry of work you already did. Without it you get rare, unreproducible duplicates that look like a bug in your logic and are not."

A webhook receiver is the first thing you will build that is exposed to the
internet and acts on what it is told. That combination deserves care.

The mechanics are simple: a URL that accepts a POST. Everything that follows is
about making it safe and reliable.

## Get a payload first

Before writing anything, see what the vendor actually sends. Point the webhook
at a throwaway URL — `webhook.site` gives you one instantly — trigger the event,
and look.

You will learn things the documentation does not tell you: the real field
names, whether the event is nested under a `data` key, what the headers are
called, whether the payload contains the full object or only an id you must
then fetch. That last one matters a lot, because if the payload carries only an
id, every webhook implies an API call and your rate-limit arithmetic changes.

## Verify the signature

**The URL is not a secret.** It appears in the vendor's dashboard, in logs on
both sides, in screenshots of the configuration, and in the browser history of
whoever set it up. Anyone who has it can send you anything.

So the vendor signs each request. They take the raw body, combine it with a
**signing secret** only the two of you know, hash it, and put the result in a
header:

```
Stripe-Signature: t=1786982400,v1=5257a869e7ecebeda32affa62cdca3fa...
```

You recompute the same hash and compare. If it matches, the sender knew the
secret and the body was not altered.

Three details decide whether this actually protects you.

**Use the raw bytes.** The signature is over exactly what was sent. If you parse
the JSON and re-serialise it, whitespace and key order change and the hash no
longer matches — even though the data is identical. Most frameworks parse the
body before your handler runs, so you must explicitly capture the raw body. The
symptom of getting this wrong is a signature failure on a payload that looks
completely correct.

**Check the timestamp.** A signature proves authenticity, not freshness. Without
a timestamp check, a captured valid request can be replayed later — the same
signed "payment succeeded" event sent again next week. Vendors include a
timestamp in the signed data; reject anything outside a few minutes.

**Compare in constant time.** Comparing two strings with `==` returns as soon as
they differ, so how long the comparison takes leaks where the first difference
was. That is enough to recover a secret one character at a time. Every language
has a constant-time comparison function; use it.

### What it proves, and what it does not

Verification proves the event **came from the vendor** and **was not altered**.

It does not prove the event is **new**. A legitimate, correctly signed event can
be delivered twice by the vendor's own retry logic. Which brings us to the next
two sections, both of which are still required.

## Acknowledge fast, process after

Vendors time out in a few seconds. If you have not responded by then, they
assume failure and retry.

So the tempting design is wrong:

```
receive → verify → call API A → call API B → write to CRM → respond 200
```

That works in testing, when everything is fast. In production, one slow
downstream call pushes you past the timeout, the vendor retries, and every event
starts arriving twice — while your logic is entirely correct.

What you want:

```
receive → verify signature → store the event → respond 200
                                             ↓
                                        process separately
```

Respond as soon as the signature verifies. Do the work afterwards — a queue, a
row in a table a worker picks up, or your platform's own async step.

This decouples the vendor's timeout from your downstream dependencies, which is
the whole point. It also means a failure *after* acknowledgement is now your
problem alone: the vendor believes it was delivered and will not retry. So
whatever processes the stored event needs the same visible-failure treatment as
any other automation — retries, a dead-letter place, and a count someone sees.

## Make it idempotent

Because delivery is at-least-once, you must assume the same event will arrive
twice, and make that harmless.

The reliable way: store the vendor's **event id** with a unique constraint.

```
1. Extract event.id from the payload
2. INSERT INTO processed_events (id) VALUES (...)
3. If the insert violates the unique constraint → already handled, respond 200 and stop
4. Otherwise → process it
```

The database enforces this atomically, so two simultaneous deliveries cannot
both get through. A read-then-write check works too and is often enough, but it
has a window between the check and the write where a concurrent duplicate can
slip past.

What does not work: an in-memory set. It is lost on restart and not shared
between workers, so it behaves perfectly in development and fails quietly in
production.

If the vendor sends no event id, derive one from stable fields — the resource
id plus the event type plus the timestamp — and be aware you are approximating.

## Test the failure paths

Before pointing a client at it, prove each protection:

- **Valid event** → accepted and processed once.
- **Tampered body** → rejected. Change one character and confirm.
- **Bad signature** → rejected.
- **Old timestamp** → rejected.
- **Same event twice** → exactly one result.
- **Malformed body** → rejected cleanly, not with a 500 and a stack trace.
- **Slow downstream** → still responds 200 quickly.

That list takes half an hour and is the difference between an endpoint you
believe works and one you have seen work. It is also, almost verbatim, what the
practical task asks for.

## When the vendor does not sign

Some vendors — usually smaller ones — offer no signature at all.

Mitigate as best you can: an unguessable URL, plus a shared secret the vendor
sends in a custom header, plus IP allowlisting if they publish their ranges.

Then be explicit with the client, in writing, that this is weaker than a signed
webhook and why. That sentence costs you nothing today and is the difference
between a known accepted risk and a thing you failed to mention.

## What to take away

See a real payload before you build. Verify the signature against the raw
bytes, in constant time, with a timestamp check. Acknowledge within a couple of
seconds and process afterwards. Key idempotency on the vendor's event id with a
unique constraint. And test the failures, not just the happy path — because the
happy path is the one case you can be certain someone else will also hit.
