You will spend more of your working life reading other people's API
documentation than writing your own code. It is worth being fast at it.

Fast does not mean reading more. It means knowing what to look for, finding
those things in order, and deliberately ignoring the rest until you need it.

## The six things

Before you write a line of code against an unfamiliar API, find these. In this
order, because each one can stop the project.

**1. The base URL.** Every endpoint hangs off it. It usually contains a version
(`/v2`, `/2024-10-01`), and that version is a promise: it is the vendor telling
you what they will not change without warning.

**2. How you authenticate.** An API key in a header? A bearer token? OAuth with
a redirect flow? This is the most common place a two-hour job becomes a two-day
one, because OAuth means a consent screen, a redirect URL, and often an
application review by the vendor. Find out now, not on the day you promised
delivery.

**3. Whether there is a sandbox.** A test environment with fake data means your
mistakes cost nothing. No sandbox means your first request touches a real
business's real records. That changes how you work — and it changes what you
should charge, because careful is slower.

**4. The endpoint you actually need.** Singular. Not the whole reference: the
one operation this job requires. You can read the other forty later, when you
have a reason.

**5. The shape of a successful response.** Find a real example. Note the field
names, the nesting, and the format of dates and money. Money in particular:
`19.99`, `1999` and `"19.99"` are three different things and only one of them
is safe to do arithmetic on.

**6. How errors are signalled.** Proper status codes, or `200 OK` with an
`error` key in the body? This determines whether your integration notices
failure at all. An API that returns `200` for failures will sail straight
through error handling that checks the status code, and the client will find
out before you do.

Six things. Twenty minutes on a well-documented API, an hour on a bad one. And
at the end of it you can quote the work honestly.

## Reference, guide, quickstart

Most documentation comes in three forms, useful at different moments.

The **quickstart** gets you a working call in five minutes by giving you
everything at once. It is genuinely useful — but copy it wholesale and you will
not know which part was load-bearing when it stops working on a client's
account. Read it, then retype the call yourself with only the pieces you
understand.

The **guide** walks through a complete task: "syncing customers", "handling
refunds". This is where the vendor tells you the things the reference cannot —
which endpoints go together, what order to call them in, what the gotcha is.
Guides are usually the highest-value pages and the least read.

The **reference** documents every endpoint exhaustively. Do not read it. Search
it, when you have a specific question.

## Make the smallest possible call

Your first request against a new API should do as close to nothing as
possible: fetch one record, or list a collection with a limit of one.

```
GET /v2/contacts?limit=1
Authorization: Bearer <token>
```

If that works, you have proven the base URL, your credentials, your network
path and your client tool all at once. Every subsequent problem is about the
specific endpoint, not the setup — and that separation is most of debugging.

If it fails, you have exactly one thing to fix, which is the point.

## When the documentation is wrong

It will be. Documentation is written once and the API keeps shipping.

The rule is simple: **the live API is right.** If the docs promise a
`customer_name` field and the response contains a `customer` object, build
against the object.

What matters as much as handling it is *writing it down*. A comment in the
workflow, a line in the handover document — anywhere the next person will find
it. Otherwise they read the same documentation, reach the same confusion, and
conclude your integration is wrong.

## Reading for fitness, not just for facts

There is a second way to read documentation, and it is the one that protects
your margin: reading to decide whether to take the job.

Things that should make you slow down and price differently:

- **No sandbox.** Every test touches live data. Slower, riskier, and you may
  need the client present.
- **Restrictive rate limits.** Do the arithmetic before quoting. A limit of
  100 requests a day cannot support five-minute polling — that is 288 requests
  before you have done anything useful.
- **No webhooks.** You will have to poll, which means something running
  constantly rather than reacting to events. That is a different cost
  structure, and a usage cost the client should be told about.
- **Errors returned as `200`.** Your monitoring will not see failures. Build
  the check yourself, and say so in the quote.
- **No filtering or pagination on a large collection.** A "simple sync" becomes
  downloading everything on every run.

None of these are reasons to refuse. They are reasons to quote the real job
instead of the imagined one — which is the difference between a project that
makes money and one that quietly eats a fortnight.

## What to take away

Six things, in order, before any code. The smallest possible first call. The
live API over the documentation, every time. And read at least once with your
commercial hat on, because the most expensive integration problems are visible
in the documentation before you have written anything.
