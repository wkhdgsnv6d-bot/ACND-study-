The previous module taught you to talk to one system. This one is about wiring
several together and walking away.

That last part is the whole difficulty. An automation you are watching is a
script. An automation running unattended on a client's business, at 3am, on
data you have never seen, is a different object — and the difference is almost
entirely about what happens when something goes wrong.

## Why design comes before tools

It is tempting to open n8n and start dragging nodes. You will have something
moving data within the hour, and it will feel like progress.

The trouble arrives later, and always in the same shape: nobody decided what
should happen when the third system is down, so the workflow does whatever the
platform's default happens to be. Nobody decided whether a duplicate is
possible, so it is. Nobody decided who finds out about failures, so nobody
does.

None of those are tool problems, and none of them are visible while the happy
path works. They are design decisions, and they are cheapest to make on paper.

## The unglamorous middle

Most of the real work in automation is not the trigger and not the action. It
is the bit in between: one system calls it `first_name`, the other wants
`firstName`; one sends `"2026-08-11"`, the other demands an ISO timestamp with
a timezone; one sends money as `19.99` and the other as `1999` cents.

That translation layer is where automations actually break, and it is the part
tutorials skip because it is specific and boring. This module does not skip it.

## Concepts before vendors

As throughout the program: the concepts here are platform-independent.
Triggers, idempotency, retries, dead letters and reconciliation exist whether
you build in n8n, Make, Zapier, or a hundred lines of code you wrote yourself.

n8n is used for examples because it is the tool Ascend runs on and because its
node model makes the data flow visible. But if the tool disappeared tomorrow,
everything in this module would still be true.
