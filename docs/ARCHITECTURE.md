# Ascend Business Mastery — Architecture

This document records the decisions behind the platform and the reasoning for
them. It is the reference for anyone (including future-you) asking "why is it
built this way?"

---

## 1. What this is

A private operating school for building **Ascend**, an AI automation and web
development agency. It has two jobs, and the balance between them shifts over
time:

- **Early**: a learning system that teaches, tests and certifies real technical
  and commercial competence.
- **Later**: a lightweight founder operating system — pipeline, revenue, MRR,
  capacity, SOPs — that happens to contain a curriculum.

The governing principle is **Learn → Build → Test → Apply → Prove → Certify**.
Watching or reading a lesson does not equal competence, and the architecture
enforces that rather than merely recommending it.

## 2. Stack

| Concern | Choice | Why |
|---|---|---|
| Framework | Next.js 16 (App Router, RSC-first) | Server components keep progress and business data on the server; static generation makes 250+ lesson pages cheap |
| Language | TypeScript, `strict` + `noUncheckedIndexedAccess` | The engines make decisions about certification and money; loose typing is not acceptable there |
| Styling | Tailwind CSS v4 + design tokens | Token-driven so the dark/light palettes stay consistent across 40+ pages |
| Components | shadcn/ui primitives, vendored | Owned in-repo, no upstream breakage, restyled to the Ascend palette |
| Icons | Lucide | Consistent stroke weight, no cartoon styling |
| Content | MDX files, Zod-validated frontmatter | See §3 |
| Database | Supabase Postgres, RLS on every table | See §4 |
| Schema authority | Drizzle (TS → SQL migrations) | Schema lives in version control, not in a dashboard |
| Charts | Recharts | Integrates with the token system; adequate for the analytics required |
| Search | MiniSearch over a prebuilt index | No search service to run or pay for |
| Palette | cmdk | Standard, accessible, small |
| Tests | Vitest (engines) + Playwright (smoke E2E) | Engines are pure and deserve real coverage |

### Next.js 16 specifics

Next 16 changed several conventions that matter here:

- `middleware.ts` is now **`proxy.ts`**, and the exported function is `proxy`.
  The runtime is Node (not Edge), which suits Supabase SSR.
- `params`, `searchParams`, `cookies()`, `headers()` and `draftMode()` are
  **async only**. Synchronous access was removed.
- Type helpers `PageProps<'/route'>`, `LayoutProps<'/route'>` and
  `RouteContext<'/route'>` are generated by `next typegen` and used throughout.
- Turbopack is the default for both `next dev` and `next build`.
- `revalidateTag` requires a `cacheLife` profile as a second argument;
  `updateTag` is the read-your-writes variant for Server Actions.

## 3. Content architecture

### The decision

**Curriculum is code. Progress is data.**

Lessons live as MDX files under `content/`. The database stores only *your
state* — what you completed, what you submitted, what you earned.

```
content/terms/term-1/09-apis-and-webhooks/
├── _module.mdx                  module overview + objectives + exam config
├── 01-what-is-an-api.mdx
└── 02-rest-and-http-methods.mdx
```

Ordering comes from the numeric filename prefix and is stripped from the public
slug, so `09-apis-and-webhooks/01-what-is-an-api.mdx` becomes
`term-1/apis-and-webhooks/what-is-an-api`. Reordering a module is a file rename;
there is no registry to keep in sync, so ordering and content cannot drift.

### Why not a database-driven curriculum

Considered and rejected:

- Every lesson edit becomes a seed script or demands an admin CRUD UI.
- Content stops being reviewable in a diff.
- Two sources of truth (seed file and live rows) drift on the first hotfix.
- The seed file becomes an unmaintainable half-million-word blob.

### Why not MDX body + a separate `.meta.ts` sibling

Type-safe, but doubles the file count and guarantees the pair drifts. One file
per lesson is the single biggest maintainability win available.

### The guardrail

`src/lib/content/schema.ts` defines the frontmatter contract in Zod.
`npm run content:check` runs it over every file and also performs cross-file
checks the per-file schema cannot:

- prerequisites resolve to real lessons
- the prerequisite graph is acyclic
- question ids are unique within a module (exams sample across a module)
- a lesson marked `complete` actually has assessment attached
- a lesson marked `complete` is not 200 words of stub

It runs as `prebuild` and in CI. **Broken content fails the build**, rather than
rendering as a blank panel at 11pm mid-study-session.

### Content honesty

Every lesson carries `status: draft | complete`.

- Draft lessons are visibly labelled in the UI.
- Draft lessons are **excluded from certification requirements** — unwritten
  content can never block a badge.
- Draft lessons are excluded from completion percentages.
- `npm run content:check` prints a per-module coverage report.

This is deliberate. Writing ~250 full-depth lessons is a long job, and the
platform should never disguise a stub as a finished lesson.

### Concepts before vendors

Per the content-accuracy rule: the timeless concept is taught in the lesson
body, and the vendor's implementation is confined to `<VendorNote>` blocks and
the Software Library. Webhooks are explained as a mechanism before n8n's
implementation of them; LLM behaviour before OpenAI's or Anthropic's API shape;
CRM modelling before HubSpot's object model.

When a vendor redesigns its interface, one component's content changes and the
concept lesson is untouched. `lastReviewed` frontmatter drives a maintenance
report for vendor-specific material.

## 4. Data architecture

### Split

Content is code (§3). Everything below is Postgres — 27 tables.

**Identity & config** — `profiles`, `settings`, `pricing_packages`
**Learning** — `lesson_progress`, `study_sessions`, `xp_events`
**Assessment** — `quiz_attempts`, `question_responses`, `exam_attempts`,
`submissions`, `lab_attempts`
**Certification** — `certifications`
**Review** — `review_cards`, `review_logs`
**Notes & portfolio** — `notes`, `projects`
**Business** — `prospects`, `prospect_activities`, `clients`, `revenue_entries`,
`costs`, `market_validation_interviews`, `business_milestones`, `sops`,
`template_instances`
**Meta** — `achievements`, `activity_log`

### What is deliberately *not* stored

Three things from the original sketch were dropped because they are derived,
and a stored copy would be a second source of truth that silently disagrees
with the rules the engines enforce:

- **XP totals** — recomputed from the `xp_events` ledger.
- **Skill levels** — computed by `skills.ts` from branch XP plus practical
  evidence. Storing a level would let it drift out of step with the
  evidence gate, which is the one rule the platform exists to enforce.
- **Streaks** — computed by `streak.ts` from `study_sessions`.

One table was merged: assignments, lesson practical tasks and term capstones
share a single `submissions` table with a `kind` discriminator, because they
share one shape — a brief, a rubric ticked criterion by criterion, and links
proving something was built.

### Security posture

- Every table carries `user_id` (or, for `profiles`, *is* keyed by the auth user
  id), has RLS enabled, and has an owner policy scoped to
  `auth.uid() = user_id` with both `USING` and `WITH CHECK`. Multi-user works
  later without a migration; multi-tenancy is not built now.
- The policy is generated by one shared helper in the schema, so a new table
  cannot ship without protection by accident.
- Data access goes through `@supabase/ssr` server clients carrying the user's
  JWT, so **RLS is genuinely enforced by the database** rather than by
  application code remembering to filter by user.
- Auth checks are layered: `src/proxy.ts` guards routes, the `(app)` layout and
  every server action re-check independently, and RLS backstops all of them.
- `getUser()` is used everywhere, never `getSession()` — the latter trusts a
  cookie the browser controls, which is not a basis for authorisation.
- `SUPABASE_SERVICE_ROLE_KEY` is used only by migration and admin scripts. It is
  never imported into anything that can reach a browser bundle.
- `xp_events` carries a unique index on `(user_id, source_type, source_id)`, so
  re-completing a lesson or re-solving a lab cannot inflate the ledger.

### Verifying RLS, twice

Policies that exist and policies that work are different claims, so both are
checked:

- `src/lib/db/rls.test.ts` parses the generated migration SQL and asserts that
  every created table enables RLS, has an owner policy scoped to the
  `authenticated` role with a `WITH CHECK` clause, grants nothing to `anon`, and
  carries a `user_id` column.
- `npm run db:verify-rls` applies the migration to a throwaway Postgres
  database, creates two accounts, and attempts real cross-account reads,
  inserts, updates and deletes. All must fail; the victim's data must survive.

### Route protection

`src/proxy.ts` — the Next 16 rename of `middleware.ts`, and it must live beside
`app/`, so under `src/` in this project. It refreshes the auth session on every
request (Server Components cannot set cookies, so without this sessions would
expire mid-study-session), redirects unauthenticated traffic to `/login`
preserving the intended destination, and rewrites everything to `/setup` when
Supabase is not configured.

### Local development

Hosted Supabase project (chosen). Three environment variables in `.env.local`
and the app is live. Migrations are applied with Drizzle against `DATABASE_URL`.

The app boots **without any credentials**: `src/lib/env.ts` never throws at
import time, and every unconfigured route rewrites to an explanatory `/setup`
screen rather than a stack trace or a sign-in form that cannot work.

## 5. The engines

Everything that computes a score, a level, a badge or a dollar figure lives in
`src/lib/engines/` as **pure functions with no I/O**. They are unit-tested, run
identically on server and client, and are the reason the platform's rules are
verifiable rather than assumed.

### `xp.ts` — the ledger

Append-only events with a deliberately lopsided award table:

| Source | XP |
|---|---|
| Lesson read | 15 |
| Knowledge check passed | 15 (+10 for a perfect first attempt) |
| Practical lab solved | 90, tapering with attempts |
| Approved assignment | 220 |
| Module exam passed | 200 |
| Project submitted with evidence | 400 |
| Certification earned | 750 |
| Real business milestone | 150–3000 |

`xp.test.ts` asserts that a read-everything-build-nothing learner reaches under
25% of total XP. That assertion exists so a future edit cannot quietly turn this
back into a clicking simulator.

### `skills.ts` — the central rule

```
level = min(xpLevel, evidenceLevel)
```

Evidence thresholds are 0 practicals for levels 0–2, **2 for level 3 (Client
Ready)**, 4 for level 4, 6 for level 5. Level 5 additionally requires a
client-ready project *and* the branch certification.

Reading every lesson in a branch therefore caps it at **level 2, Practised** —
regardless of XP. The UI always shows *why* a skill is capped and exactly what
would lift it.

### `certification.ts` — declarative requirements

Certifications are a list of typed requirement predicates evaluated against your
data. There is no "mark as certified" code path; a certification exists only as
the output of `evaluateCertification`.

Requirement kinds: `lessons-complete`, `exam-passed`, `labs-solved`,
`assignments-approved`, `project-submitted` (with required evidence kinds),
`skill-at-least`, `certification-earned`, `business-milestone`,
`business-metric`.

Status flows Not Started → Learning → Practical Required → Exam Required →
Submitted → Passed / Needs Improvement → Certified, derived from which
*category* of requirement is outstanding.

A test asserts that **no certification can be satisfied by lesson completion
alone** — every one carries a practical, exam or business requirement.

**Honest limitation.** With no external examiner, practical evidence is
self-attested. What the engine guarantees is that bypassing a requirement is a
deliberate, recorded act rather than an accident: evidence URLs are required
fields, rubric criteria are ticked individually, and every evaluation stores
what satisfied it. The AI Study Assistant (Phase 10) is designed to grade
submissions against those same rubrics, which is where genuine external checking
arrives.

### `unlock.ts` — two kinds of lock

**Prerequisite locks** are pedagogical, cheap to satisfy, and always name the
exact lesson that opens them. No artificial gates.

**The Term 4 lock** is strategic. Thresholds are configurable in Settings and
default to *any one of*: $10,000 monthly revenue · $3,000 MRR · 5 active clients
· 1 regular contractor. The lock screen shows each threshold with your current
value and a progress bar, plus the message:

> Build the machine before learning how to manage a company you don't yet have.

A manual override exists, requires a written reason, and stores it.

### `streak.ts`

Operates on local calendar day strings (`YYYY-MM-DD`), not `Date` objects — a
session at 11pm in Sydney and one at 1am next morning are different days to the
learner and the same UTC day to a naive implementation. Requires 10 real minutes
(opening the dashboard is not studying) and forgives one missed day per rolling
week, because a single sick day breaking a 40-day streak is where people quit.

### `srs.ts`

SM-2 adapted. Cards come from two sources: concepts a lesson declares, and
**concepts you got wrong in a quiz**. The second is the important one — it turns
a failed quiz from a score into a study plan. Mistake-born cards return sooner
and are prioritised in a session.

### `finance.ts`

Margins, LTV, CAC, churn, MRR movement with net revenue retention, capacity,
hiring triggers and project estimation. Money is handled in whole cents
throughout and converted at the edges.

This engine is shared by the Business Lab calculators *and* by worked exercises
inside lessons, which is what makes the spec's rule work: a lesson asking you to
compute the Growth package's gross margin reads the same package record the
calculator does. The exercise is about your business, not a textbook company.

## 8. Development rules

1. Never delete working functionality unnecessarily.
2. Inspect the existing implementation before major architectural changes.
3. Keep components modular; engines pure and I/O-free.
4. `any` requires a written justification.
5. Handle loading, empty and error states — all three, every time.
6. Validate every form with a shared Zod schema on both client and server.
7. Secrets stay server-side. `NEXT_PUBLIC_` is a promise that a value is public.
8. Never expose the service-role key to the frontend.
9. Maintain mobile responsiveness and keyboard accessibility.
10. Run `npm run verify` (content + typecheck + lint + test) before committing.
11. Fix errors rather than suppressing them. `ignoreBuildErrors` stays false.
12. Do not replace a working feature with a placeholder.
13. Do not claim something works without running it.

## 9. Commands

```bash
npm run dev              # development server
npm run build            # production build (runs content:check first)
npm run verify           # content + typecheck + lint + test
npm run content:check    # validate curriculum, print coverage report
npm run content:strict   # as above, warnings fail
npm test                 # engine, schema and RLS-policy tests

npm run db:generate      # regenerate SQL migrations from the Drizzle schema
npm run db:migrate       # apply migrations (needs DATABASE_URL)
npm run db:verify-rls    # prove RLS isolates accounts, on a throwaway database
npm run db:studio        # browse the database
```

## 10. Navigation and honest scope

`src/lib/navigation.ts` marks each sidebar item with the phase that builds it.
Items above `CURRENT_PHASE` render disabled with the phase shown, rather than
linking to twenty placeholder pages. The sidebar tells the truth about what
exists; nothing pretends to be a working feature.
