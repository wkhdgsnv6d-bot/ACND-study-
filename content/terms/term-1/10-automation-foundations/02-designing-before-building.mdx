The difference between an automation that survives a year and one that quietly
breaks in month two is decided before anything is built.

Not because design produces a better workflow — because it is the only point at
which the failure questions get asked at all.

## Why the happy path is not the design

Open a tool and start building, and you will build the path where everything
works. It is the path the client described, the one the demo shows, and the one
you can hold in your head.

Then production supplies the others: the API is down; the payload has a field
you have never seen; the same event arrives twice; a required field is empty;
the client's ops manager pastes a phone number with spaces in it.

The workflow does *something* in each of those cases. It does whatever the
platform's default is — which is usually "stop and go red", or worse,
"continue with empty data". Nobody chose that behaviour. It was assigned by
omission.

**Design is the act of choosing it deliberately.**

## The one page

Seven things. On a small workflow it takes ten minutes.

**1. The trigger**, and which of the four types it is. Note the latency this
gives you, because that is what the client will actually experience.

**2. The steps, in order.** Plain sentences. "Look up the contact by email.
If none exists, create one. Create a deal linked to it."

**3. The data contract at each boundary.** The real field names, types and
formats on both sides. This is the least glamorous part of the design and the
part that saves the most time, because it forces you to look at real payloads
before you build against imagined ones.

**4. A failure decision for every step.** Covered below. This is the page that
matters.

**5. The source of truth**, if anything is bidirectional.

**6. Who finds out, and how.** A name, a channel, a timeframe. "Nobody" is a
valid answer for something low-stakes, as long as it was chosen.

**7. The manual fallback.** When the automation cannot complete, what does a
human do? If the answer is "nothing, the work is lost", say so explicitly — the
client may accept that, and they may not.

## The failure table

Go step by step. For each one, two questions:

- What happens if this **fails**?
- What happens if this **half-succeeds** — the request that timed out after the
  server had already processed it?

Then decide: **retry**, **skip**, or **stop**. And: where does the record go if
it is not processed?

| Step | Fails | Half-succeeds | Decision |
|---|---|---|---|
| Receive webhook | Vendor retries | Same event twice | Idempotent on booking id |
| Look up contact | API down | — | Retry 3× with backoff, then dead-letter |
| Create contact | Validation error | Contact created, response lost | Look up before create; retry safe |
| Create deal | API down | Deal created, response lost | Idempotent on booking id; retry |
| Send email | Provider down | Email sent, response lost | Retry once; log and continue |

That table is the design. Everything above it is context.

Notice that filling it in forces the idempotency question at every step — which
is the question the previous module spent three lessons on, arriving here as a
row in a table.

## Source of truth

Any time data flows both ways, one question has to be answered before you
build: **when both systems change the same record, which wins?**

Without an answer, the winner is whichever write happened to land second. The
other change disappears — no error, no log, no way to know it happened.

There are three workable answers:

- **One system owns everything**, the other follows. Simplest, and usually
  right.
- **Field-level ownership.** Bookings own appointment times; the CRM owns
  contact details. Matches how people actually work, and is more to build.
- **Conflicts go to a human.** Safest, and only viable at low volume.

This is a business decision, not a technical one, so the client answers it. Your
job is to make sure they are asked — and to write the answer down where the
next person will find it.

## Writing it for the client

The design has two audiences and they need different documents.

**For you**: the full page, with field names and the failure table.

**For the client**: four to six sentences, no jargon.

> When a booking comes in through the website, the system creates the customer
> in your CRM and adds the booking as a deal, then messages the team channel.
> It usually happens within about ten seconds. If your CRM is unavailable, it
> tries again for a few minutes; if it still cannot get through, the booking
> goes into a holding list and you get an email — nothing is lost. Duplicate
> bookings are ignored, so a customer clicking twice cannot create two records.
> The only thing needing you is the holding list, which should normally be
> empty.

A client can read that and say "actually, if the CRM is down I want a text, not
an email". That correction costs a minute now and a rebuild later.

They cannot say that about a node diagram.

## What to take away

Design is not documentation of what you will build. It is the point at which
the failure behaviour, the conflict rules and the notification path get decided
by someone rather than assigned by default. Write the failure table, decide the
source of truth, and send the client sentences they can argue with.
