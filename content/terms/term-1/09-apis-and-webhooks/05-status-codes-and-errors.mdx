terminology:
  - term: "Status code"
    definition: "A three-digit number in every HTTP response indicating broadly what happened. The first digit gives the family."
  - term: "Transient error"
    definition: "A failure caused by a temporary condition — a timeout, an overloaded server, a rate limit — that may succeed if tried again."
  - term: "Permanent error"
    definition: "A failure caused by something wrong with the request itself, which will fail identically no matter how many times it is retried."
  - term: "Exponential backoff"
    definition: "Waiting progressively longer between retries — one second, then two, then four — rather than retrying at a fixed interval."
  - term: "Jitter"
    definition: "A small random amount added to a backoff delay, so that many clients recovering from the same outage do not all retry in the same instant."
  - term: "Dead letter"
    definition: "A place failed items are put after retries are exhausted, so they can be inspected and reprocessed rather than lost."

An API tells you what happened twice: once in the status code, and once in the
body. Most people read the first and skip the second, then spend an hour
guessing at something the response already said.

## Read the first digit

There are dozens of status codes. You do not need to memorise them, because the
first digit tells you almost everything.

**2xx — it worked.** `200 OK`, `201 Created` for something new, `204 No
Content` for a successful delete with nothing to return.

**3xx — go somewhere else.** Redirects. Most HTTP clients follow them
automatically. Worth noticing if an API redirects `http` to `https`, because
some clients drop the `Authorization` header across a redirect and you get a
mysterious 401.

**4xx — the request was wrong. Your fault.** It will fail identically if you
send it again unchanged.

**5xx — the server failed. Their fault.** Your request may have been perfect.
Worth retrying.

That 4xx/5xx line is the one that matters operationally, because it decides
whether you fix something or wait.

### The 4xx codes worth knowing by name

- **400 Bad Request** — malformed. Broken JSON, wrong type.
- **401 Unauthorized** — we do not know you. Bad or expired credential.
- **403 Forbidden** — we know you, and no. Missing scope.
- **404 Not Found** — no such resource. Also, frequently, a wrong URL.
- **409 Conflict** — clashes with current state. Duplicate email, version
  mismatch.
- **422 Unprocessable Entity** — understood, but the contents are invalid. A
  missing required field, a date in the wrong format. The most informative 4xx,
  because the body almost always names the field.
- **429 Too Many Requests** — rate limited. The odd one out: a 4xx that
  **is** worth retrying, after waiting.

### The 5xx codes

- **500 Internal Server Error** — something broke on their side.
- **502 Bad Gateway** — a proxy got an invalid response from upstream.
- **503 Service Unavailable** — temporarily unable to serve. Often deployment
  or overload.
- **504 Gateway Timeout** — a proxy waited for upstream and gave up.

For your purposes these are one thing: *the server failed, try again shortly.*

## The body is where the answer is

`422` tells you the payload was rejected. It does not tell you which of your
twelve fields caused it. The body does:

```json
{
  "error": "validation_failed",
  "details": [
    { "field": "phone", "message": "must be in E.164 format, e.g. +61412345678" }
  ]
}
```

That is a complete diagnosis, and it takes a second to read. The habit worth
building is: **look at the body before you change anything.** Most automation
platforms show you the status prominently and hide the body one click away,
which is precisely backwards.

## Retry the right things

A retry setting is one toggle in most automation platforms, which is why it so
often ends up applied to everything.

**Retry:** 5xx, 429, network timeouts.
**Never retry:** 400, 401, 403, 404, 422.

Retrying a 422 does not fix the missing field. It just fails more slowly, and
on a rate-limited API it can escalate into a 429 — turning a clear error into a
confusing one.

One exception worth building deliberately: on a `401`, if you hold a refresh
token, refresh once and retry once. Beyond that, stop — repeatedly presenting a
bad credential is how applications get locked out.

### Backoff and jitter

When you do retry, wait longer each time:

```
attempt 1 → wait 1s
attempt 2 → wait 2s
attempt 3 → wait 4s
attempt 4 → wait 8s
then stop
```

Add a small random offset — **jitter** — to each wait. The reason is not
theoretical. When a popular API has a brief outage, every integration in the
world starts retrying. Without jitter they all retry at the same instant, and
the stampede keeps the server down. This is a real failure mode with a name,
and the fix is a few hundred milliseconds of randomness.

If the response carries a `Retry-After` header, **obey it**. That is the server
telling you exactly how long to wait, and it beats any schedule you invented.

## Failing visibly

Here is the most expensive mistake in this lesson, and it does not look like a
mistake at the time.

You wrap the API call in error handling so the workflow does not stop. The red
error disappears. The workflow runs green every day. Six weeks later a customer
asks why they never got their confirmation, and you discover the integration
has been failing since the API changed a field name — silently, hundreds of
times.

**A workflow that stops is a problem you find in an hour. A workflow that hides
failures is a problem you find in six weeks, from the client.**

Stopping is not the only option, and it is not the best one. What you actually
want:

1. **Keep processing the good records.** One bad row should not block four
   hundred good ones.
2. **Put failures somewhere.** A dead-letter table, a spreadsheet, a Slack
   channel — anywhere they can be inspected and replayed. The failed item must
   survive.
3. **Surface a count.** "412 synced, 5 failed" is a sentence a client can act
   on. A green tick is not.
4. **Alert on the pattern, not the instance.** One failure is noise. Five in an
   hour, or a run where everything failed, is a phone call.

That design gives you the resilience of continuing and none of the blindness.

## The API that returns 200 for errors

Some APIs — usually older ones — return `200 OK` with the failure inside the
body:

```json
{ "status": "error", "message": "Invalid customer reference" }
```

Every convention in this lesson breaks against those. Your status check passes.
Your monitoring is quiet. The data never arrives.

The only defence is to find out early. When assessing a new API, **deliberately
send a bad request and look at what comes back.** If it is a 200, you now know
to check the body shape on every call, and you can say so in the quote — it is
extra work, and it is work you would otherwise do for free at 3am.

## What to take away

The first digit tells you whose fault it is. The body tells you what to fix.
Retry 5xx, 429 and timeouts with backoff and jitter; never retry a request the
server has already understood and rejected. And build for the failure to be
seen — by you, ideally, and never first by the client's customer.
