Every automation fails. The question a client is really buying an answer to is
what happens next.

## Two kinds of failure

They need opposite responses, and conflating them is the most common design
error in this module.

**Record-level.** One item cannot be processed — a malformed phone number, a
missing required field — while everything else would be fine.

→ **Continue.** Dead-letter that record. Process the rest.

**Run-level.** The run itself cannot work — credentials rejected, destination
down, the trigger firing with no data.

→ **Stop.** Alert. Nothing will succeed until someone acts.

Getting this backwards is expensive in both directions. Stop the run for one bad
phone number and 397 good contacts do not sync. Continue through a 401 and you
fill the dead-letter store with 200 perfectly good records while burning rate
limit on failures.

The test is simple: **would the next record succeed?** If yes, it is
record-level. If no, it is run-level.

## The dead letter

When a record cannot be processed, it has to go somewhere. Not skipped — kept.

Each entry needs four things:

- **The original payload**, exactly as received.
- **The reason**, in words. "Phone number not in E.164 format", not "error".
- **The step** it failed at.
- **The timestamp.**

The payload alone is not enough. Without the reason, whoever opens it is
debugging from scratch.

It does not need to be sophisticated. A database table is ideal; a spreadsheet
the workflow appends to is entirely adequate for a small client and has the
advantage that they can read it.

What matters is that **the record survives** and that someone can put it back
through once the cause is fixed. Build the replay path at the same time — a
tick-box column, or a "retry failed records" workflow. A dead-letter store with
no replay is a list of things you have lost, written down.

One security note that is easy to miss: this store contains real customer data
sitting outside the systems meant to hold it. Access-control it, decide a
retention period, and empty it. A dead-letter sheet nobody clears becomes an
unmonitored copy of the client's customer list.

## Idempotency, again

The theme of the whole term arrives here as a build step.

Your workflow **will** be triggered twice for the same thing — a vendor retry, a
customer double-clicking, a manual re-run, a platform hiccup. Make it harmless:

1. Take a stable id from the payload — the booking id, the vendor's event id.
2. Before doing anything, check whether that id has been processed.
3. If it has, stop successfully. Not an error; there is nothing to do.
4. Otherwise, record it and proceed.

The check must be atomic where possible — a unique constraint rather than a
read-then-write — because two simultaneous deliveries can otherwise both pass
the check.

If the payload has no stable id, derive one from fields that will not change:
source system, record id, event type. Do not use the timestamp alone; two
retries of the same event can carry different receipt times.

## Alerting people will read

The failure mode here is human. Alert on everything and the channel is muted
within a fortnight — and then the alert that mattered arrives in a channel
nobody reads. Everyone believes they are covered. Nobody is.

Three tiers:

**Urgent, immediately.** Run-level failures. Nothing is working. Someone needs
to act now.

**Threshold, hourly.** "12 records failed in the last hour" when the norm is
two or three. A rate change means something has changed — an API deployed, a
form field renamed.

**Digest, daily.** "3 records failed yesterday, here they are." Routine, needs
attention eventually, does not need a notification at 2am.

Set the threshold from the actual baseline, not from a round number. If two or
three failures a day is normal, alert at five in an hour — not at ten percent,
which at 2,000 records a day is 200 failures before anyone hears.

## The runbook

The last piece is the one that decides whether you have built a service or a
dependency.

Write, in plain language: what the alert means, where to look, how to tell a
data problem from a system problem, what to do about the common case, and when
to stop and call you.

Two paragraphs is enough. What it must do is let the client resolve the routine
case without you — which is better for them and, in the end, better for you,
because the alternative is being rung about a malformed phone number on a
Saturday.

And be explicit that **nothing is lost while records sit in the dead-letter
store.** That single sentence is the difference between a client who deals with
it Monday and a client who panics on Sunday night.

## What to take away

Ask whether the next record would succeed: that decides record-level from
run-level. Dead-letter with the reason, not just the payload, and build replay
at the same time. Key idempotency on a stable id. Alert in three tiers so the
urgent one is still believed. And write the runbook, because a recovery only you
can perform is not a finished piece of work.
