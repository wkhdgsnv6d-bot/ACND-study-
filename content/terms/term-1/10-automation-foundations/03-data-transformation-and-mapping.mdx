  - key: money-representation
    prompt: "How should money move through an integration, and why?"

  - key: empty-null-missing
    prompt: "What is the difference between missing, null and empty string, and why does it matter?"
    answer: "Missing means the field was not in the payload at all — often because the API changed or the object type differs. Null means present and explicitly set to nothing. Empty string means present and set to a value that happens to be empty, usually a person leaving a form field blank. They mean different things and most platforms treat all three as falsy, so a single check collapses them. That is how 'the API stopped sending this field' gets silently handled as 'the customer did not fill it in'."
  - key: validate-at-boundary
    prompt: "Why validate before sending rather than relying on the destination to reject bad data?"
    answer: "Because the destination's rejection arrives as a generic error deep inside a run, often after other steps have already written data — so you get partial state and an error that does not say which field was wrong. Validating at the boundary means the failure names the field, happens before anything has been changed, and can route the record to a dead-letter store with a readable reason. It also means you can tell the difference between 'this record is bad' and 'the destination is down', which need completely different responses."

The trigger is a node. The destination is a node. The work is in between, and
it is where integrations actually break.

This lesson is the boring one that saves the most time.

## Field names are the easy part

`first_name` to `firstName` is trivial. Every platform has a mapping interface
for it.

The problems are types, formats, and the difference between empty and absent.

## Money

Store money as an **integer in minor units** — cents — and convert only for
display.

```
$19.99  →  1999
```

The reason is that binary floating point cannot represent `0.1` exactly. Sum
enough decimal line items and the total drifts by a fraction of a cent, which
eventually crosses a rounding boundary and produces an invoice a cent out. There
is no error and no obvious cause — just a number that is wrong and a client who
noticed.

Integers are exact. Do all arithmetic in cents and divide by 100 at the last
moment.

The other half: **always carry the currency.** A bare number is a bug waiting
for the client's first international customer.

## Dates

Two systems can both use ISO-looking strings and still disagree.

```
"2026-09-01 09:30:00"       ← no timezone. What moment is this?
"2026-09-01T09:30:00Z"      ← UTC. Unambiguous.
"2026-09-01T09:30:00+10:00" ← Brisbane. Unambiguous.
"01/09/2026"                ← 1 September or 9 January?
```

The first is the dangerous one, because it looks fine. Treat it as UTC when it
is actually local time and every booking shifts by hours — still plausible,
completely wrong, and discovered when a customer arrives at the wrong hour.

The rule: **parse to a known representation, then format for the destination,
and always know the timezone.** If the source does not tell you, find out from
the vendor rather than assuming. "Probably UTC" is not an answer you want to
have given.

## Names

Do not split names on the first space.

```
"Mary Jane Watson"  →  first: "Mary", last: "Jane Watson"
"van der Berg"      →  breaks
"Prince"            →  breaks
"李 明"              →  family name first
```

If the destination demands separate fields and the source gives you one, split
on the **last** space, accept that you will be wrong sometimes, and never make
the split irreversible — keep the original string somewhere.

Better: change the form to collect the fields the destination needs. Fixing the
source is often cheaper than transforming forever.

## Phones

Normalise to **E.164** at the boundary and stop thinking about it:

```
"(04) 1234 5678"    →  "+61412345678"
"0412 345 678"      →  "+61412345678"
"+61 412 345 678"   →  "+61412345678"
```

Strip everything that is not a digit or a leading plus, then apply the country
code. You need to know the default country — ask, do not assume from the
client's address.

## Missing, null, and empty

These are three different things and most platforms make all three falsy, so
one check appears to catch them all.

```json
{ "company": "Acme" }   ← present, has a value
{ "company": "" }       ← present, empty. User left the field blank.
{ "company": null }     ← present, explicitly nothing.
{ }                     ← absent. The API changed, or this object type differs.
```

That last case is the one that bites. This looks reasonable:

```js
const company = payload.company || "Unknown";
```

Then the API nests the field, `payload.company` is `undefined` for every
record, and every contact — including ones with a real company — becomes
"Unknown". Silently, at scale.

**Decide what each state means, per field, and handle absence separately from
emptiness.** Absence usually means something structural changed, which should be
loud.

The same trap catches zero and `false`: `quantity || 1` turns a legitimate zero
into one.

## Nested data

Payloads are rarely flat:

```json
{
  "customer": { "name": { "first": "Dana", "last": "Okonkwo" } },
  "items": [ { "sku": "A1", "qty": 2 } ]
}
```

Two things to decide. **How deep can you safely reach** — `customer.name.first`
breaks if `name` is absent, so use whatever safe-navigation your platform
offers. And **what happens with arrays**: one order with three items might
become three CRM rows, or one row with a summary. That is a design decision, and
it belongs in the design document rather than being discovered mid-build.

## Validate at the boundary

Validate **immediately after receipt, before anything writes anywhere.**

Check: required fields present; types correct; formats valid; values within
plausible ranges.

If validation fails, the record goes to the dead-letter store with a message
naming the field, and nothing has been written yet.

The alternative — letting each destination reject what it dislikes — means you
may already have written to two other systems, the error is generic, and you
cannot distinguish "this record is bad" from "the destination is down". Those
two need opposite responses: one should be dead-lettered, the other retried.

Validation is also a security boundary. Data from a form or webhook is untrusted
input. Check lengths and types before writing, never concatenate a received
value into a query, and remember that a spreadsheet cell beginning with `=` is a
formula — which is how a CSV export becomes an attack on whoever opens it.

## What to take away

Money in integer cents with a currency. Dates parsed with a known timezone.
Names not split unless forced. Phones normalised once. Missing, null and empty
treated as three different things. And validation at the boundary, before
anything is written, so failures name the field instead of appearing three steps
later as a generic error.
