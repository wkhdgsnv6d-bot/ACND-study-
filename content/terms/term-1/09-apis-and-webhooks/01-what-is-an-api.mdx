## Start with the problem, not the definition

A plumbing business runs a booking system. A customer fills in a form on the
website. Somebody needs to get that enquiry into the booking system, into the
CRM, and in front of whoever is on the tools that afternoon.

Right now a person does it. They read the email, retype the details into the
booking system, and text the plumber. It takes four minutes, it happens eleven
times a day, and about once a week something gets missed.

You have been asked to fix it. To do that, your code needs to put a booking into
their booking system. But you do not work for the company that built that
booking system. You cannot open its database. You do not know what language it is
written in, and you should not have to care.

What you need is a way to say *"create a booking with these details"* to a
system you know nothing about, and have it work.

That is what an API is for.

## The definition, now that it means something

An **API** — Application Programming Interface — is a defined set of operations
that a piece of software exposes so other software can use it, without needing
to know how it works inside.

Two words in that sentence are doing the work.

**Defined** means the operations are fixed and documented. The booking system
does not accept arbitrary instructions. It publishes a list: create a booking,
list bookings, cancel a booking, update a customer. If the operation you want is
not on that list, you cannot do it, no matter how clever you are.

**Without needing to know how it works inside** is the whole point. The vendor
can rewrite their entire backend next year. As long as the published operations
still behave the same way, your integration keeps working. This is why APIs
exist at all: they are a promise about behaviour that survives changes in
implementation.

## The request/response cycle

Nearly every API you will meet at Ascend works over HTTP, the same protocol your
browser uses. The interaction has exactly two halves.

You — the **client** — send a **request**. The vendor's system — the **server**
— sends back a **response**. That is the whole cycle. Nothing is persistent; the
server does not remember you between calls unless you tell it who you are each
time.

A request has four parts:

- **The method** — what kind of operation. `GET` to read something, `POST` to
  create something. There are others, and they get a lesson of their own.
- **The URL** — which endpoint you are addressing. `https://api.example.com/v1/bookings`
  is a different operation from `https://api.example.com/v1/customers`.
- **Headers** — metadata about the request. Who you are (authentication), what
  format you are sending, what format you want back.
- **The body** — the actual data, on requests that carry any. A `GET` usually
  has none; a `POST` creating a booking carries the booking details.

A response has three:

- **A status code** — a three-digit number saying how it went. `200` means fine.
  `404` means the thing you asked for is not there. `401` means the server does
  not know who you are.
- **Headers** — metadata about the response, including how much of your rate
  limit you have left.
- **A body** — the data, almost always JSON.

Here is what that looks like concretely. A request:

```http
GET /v1/bookings?date=2026-08-14 HTTP/1.1
Host: api.example.com
Authorization: Bearer sk_live_9f2c...
Accept: application/json
```

And the response:

```http
HTTP/1.1 200 OK
Content-Type: application/json
X-RateLimit-Remaining: 97

{
  "data": [
    {
      "id": "bk_8812",
      "customer": "Marina Okafor",
      "scheduled_for": "2026-08-14T09:30:00+10:00",
      "status": "confirmed"
    }
  ],
  "has_more": false
}
```

You asked for the bookings on a given date. You said who you were in the
`Authorization` header. You got back a `200`, a note that you have 97 requests
left this window, and a JSON body containing one booking.

That is the entire mechanism. Everything else in this module — methods,
authentication schemes, status codes, pagination, rate limits, webhooks — is
detail hung on this frame.

## What an API is not

Three distinctions are worth nailing down now, because conflating them causes
real confusion later.

**An API is not a website.** Both may be reached over HTTP, and an API's
documentation is usually a website, which muddies things. But a website returns
HTML designed for a person to look at. An API returns structured data designed
for software to act on. If you visit an API endpoint in your browser and see a
wall of JSON, you are seeing the difference.

**An API is not a database.** It usually sits in front of one, but it exposes a
deliberately controlled set of operations rather than raw table access. That
control is the feature. It is also why the API sometimes will not give you
something you can plainly see in the vendor's own interface — the interface has
privileges and internal access that you do not.

**An API is not a webhook.** With an API, *you* ask and the server answers. With
a webhook, the server contacts *you* when something happens. They are opposite
directions of travel, and choosing between them is a design decision you will
make on nearly every Ascend build. That gets its own lesson.

## Why a vendor bothers

It is a fair question, and clients do ask it. Opening a system to outside
software sounds like pure downside for the vendor.

It is not, for three reasons. A product that integrates with the tools a business
already uses is far easier to sell than one that stands alone. A customer who has
built integrations around a product finds it expensive to leave, which improves
retention. And an API lets the vendor serve a long tail of customer-specific
needs without building any of it — you build the plumbing business's particular
workflow, not them.

The risk is managed rather than accepted. Access requires credentials the vendor
issues and can revoke instantly, and those credentials are normally scoped so a
given integration can only reach the data it genuinely needs.

That last point is not just the vendor's concern. When you hold a client's API
credentials, you are holding access to their customers' data. Treat it
accordingly, starting today.
