The first API you meet will feel like its own thing to learn. So will the
second. Somewhere around the fourth, you notice they are all the same shape, and
from then on a new API is a few hours of work rather than a few days.

That shape has a name.

## Nouns in the address, verbs in the method

REST is an architectural style, and the part that matters day to day is a
single idea: **the URL names a thing, and the HTTP method says what to do
to it.**

```
GET    /contacts        list the contacts
POST   /contacts        create a contact
GET    /contacts/42     fetch contact 42
PATCH  /contacts/42     change part of contact 42
PUT    /contacts/42     replace contact 42
DELETE /contacts/42     delete contact 42
```

Six operations, one noun. The alternative — which plenty of older APIs use —
puts the action in the URL: `/getContact`, `/createContact`, `/updateContact`,
`/deleteContact`. That works, but every operation is a new name you have to
look up, and there is no pattern to generalise from.

With REST, once you have seen `/contacts` you can make a confident guess at
`/companies`, `/deals` and `/invoices` without opening the documentation again.

## The methods, and when each is wrong

**GET** retrieves. It must not change anything — that is what "safe" means in
HTTP — which is why browsers and proxies feel free to cache it and why a
crawler following links cannot damage your data. If you ever find yourself
building an endpoint where `GET /orders/42/cancel` cancels an order, you have
built something a search engine's crawler can quietly destroy.

**POST** creates. It is the one method in common use that is **not**
idempotent: each call makes another thing. Sending `POST /contacts` twice gives
you two contacts.

**PUT** replaces the entire resource with what you send. Fields you leave out
are, on a strict API, cleared. It is idempotent — sending the same body five
times leaves exactly the state that body describes.

**PATCH** changes only what you send. It is the right choice for the
overwhelmingly common case of "one field changed", and it is the method people
most often skip because POST appeared to work.

**DELETE** removes. It is idempotent in the sense that matters: after the first
call the thing is gone, and after the fifth it is still gone. The later
responses may be `404` rather than `204`, but the end state does not change,
which is the actual definition.

## Idempotency is a retry question

Idempotency sounds like a word from a specification. It is really a question
about failure, and it is the reason this lesson is in a module about
automation.

Here is the situation you will meet, probably within your first month of
building automations for someone else. Your workflow sends a request. The
server receives it, does the work, and starts sending the response. Somewhere
between the two, the connection drops. Your automation platform sees a timeout.

It does not know whether the work happened.

The only sane default is to retry — and most platforms will do it for you,
often without asking. So the question becomes: **what happens if this request
runs twice?**

- `GET` — nothing. Retry freely.
- `PATCH /contacts/42 {"email": "..."}` — the email is set to the same value
  again. Harmless.
- `DELETE /contacts/42` — already gone. Harmless.
- `POST /invoices {...}` — **the client is invoiced twice.**

That last line is the one that reaches the client before it reaches you. It is
also why serious APIs offer an *idempotency key*: a value you generate and send
with a POST, which the server remembers, so a retry with the same key returns
the original result instead of creating a second thing. Stripe's is the
best-known implementation. If an API you are integrating offers one and your
automation creates anything financial, use it.

## Path parameters and query parameters

Two kinds of value end up in a URL, and they mean different things.

A **path parameter** identifies which resource you mean. The `42` in
`/contacts/42` is not a filter — it is part of the address.

A **query parameter** modifies what you get back from a collection: filtering,
sorting, pagination, choosing fields.

```
GET /contacts?company_id=17&status=active&limit=20&sort=-created_at
```

The rule of thumb: if removing the value would leave you asking for a
*different thing*, it belongs in the path. If it would leave you asking for
*more of the same thing*, it belongs in the query string.

This is also a security boundary, which is why the security note above matters
more than it looks. Query strings are logged — by the server, by proxies, by
your own monitoring — and they appear in browser history. A key in a query
string is a key in a log file that somebody's ops team can read.

## When it is not really REST

Plenty of production APIs are "RESTish". They will have an endpoint like
`POST /deals/42/close`, or use POST for reads because the query is too big for
a URL, or return `200 OK` with an error inside the body.

This is not a reason to complain. It is a reason to **read the documentation
rather than assume**, and to check two things specifically before you build on
it:

1. Which operations are safe to retry, since you cannot infer it from the
   method any more.
2. How errors are signalled, since a `200` containing `{"error": "..."}` will
   sail straight through error handling that only checks the status code.

Both of those are the next two lessons.

## What to take away

The shape is worth internalising because it makes every future API cheap. But
the part that will actually change your work is the retry question. Before you
wire any request into an automation, ask what happens if it runs twice — and if
the answer is "the client gets two of something", make sure you have an
idempotency key or a check-before-create step.
